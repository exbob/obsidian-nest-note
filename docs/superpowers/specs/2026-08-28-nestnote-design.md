# NestNote 设计文档

## 1. 概述

NestNote 是一个 Obsidian 插件，将“文件夹即文档”作为文档组织模型。每个文档目录包含唯一的 `index.md`、`attachments/` 目录以及任意数量的子文档目录。插件通过自定义侧边栏展示和操作文档树，同时保留 Obsidian Vault 文件作为唯一数据源，不引入额外索引数据库。

插件名称：

- 显示名称：NestNote
- 插件 ID：`nest-note`

## 2. 已确认的范围

- 管理整个 Vault 根目录。
- 支持新建文档，并自动识别已有的完整文档目录。
- 不完整目录、普通 Markdown 文件和其他非文档文件均忽略。
- 支持根文档和子文档。
- 支持打开、新建、重命名和删除文档。
- 删除任何文档前均显示确认提示，确认后将整个目录移入 Obsidian 回收站。
- 使用标准 Markdown 相对链接。
- 自动链接只维护受控区域，不修改用户正文。
- 兼容 Obsidian 原生“插入附件”命令，创建附件后自动归档。

## 3. 文档模型

### 3.1 目录结构

```text
Work/
├── index.md
├── attachments/
├── 文档1/
│   ├── index.md
│   └── attachments/
└── 文档2/
    ├── index.md
    └── attachments/
```

目录的直接子项中满足以下条件时，该目录被识别为文档：

1. 目录中存在 `index.md`。
2. 目录中存在 `attachments/` 目录。
3. 目录名称是文档名称。

`attachments/` 是保留目录名，不会被识别为子文档。其他目录只有在自身满足完整文档条件时才作为子文档显示。

### 3.2 Frontmatter

新建文档时，`index.md` 的头部写入：

```yaml
---
name: Work
created: 2026-08-28T19:00:00+08:00
---
```

- `name` 默认等于所在目录名称。
- 目录名称是名称的唯一权威来源。
- 目录重命名后，同步更新 `name`。
- `created` 只在首次创建时写入，后续不自动修改。
- 如果缺少 Frontmatter，插件在正文前补充完整 Frontmatter，不修改原正文。
- Frontmatter 解析异常时不覆盖正文，并提示元数据异常。

## 4. 侧边栏与操作

插件注册自定义侧边栏视图，递归显示所有完整文档。

### 4.1 展示

- 文档名称来自目录名称。
- 子文档以树形结构显示。
- 点击文档打开对应的 `index.md`。
- 普通文件和不完整目录不显示。
- Vault 变化后自动触发全量重新扫描，并尽量保留展开和选中状态。

### 4.2 新建

新建入口按父路径判定方式分为以下几类：

| 入口 | 父路径 |
|------|--------|
| 侧边栏工具栏「新建文档」按钮 | 始终在 Vault 根目录 |
| 命令 `nestnote:new-document`（**NestNote：新建文档**） | 始终在 Vault 根目录 |
| 侧边栏某文档行上的「新建子文档」按钮 | 以该行文档为目标父节点 |
| 命令 `nestnote:new-child-document`（**NestNote：新建子文档**） | 以当前活动文件所属文档为父节点；须先打开父文档的 `index.md`，否则提示并中止 |

侧边栏工具栏「新建文档」与命令 `nestnote:new-document` 不受侧边栏选中态影响。命令 `nestnote:new-child-document` 不读取侧边栏选中态，仅依赖编辑器中当前打开的 `index.md`。

创建时自动生成目录、`index.md` 和 `attachments/`。名称包含路径禁止字符（`/ \ : * ? " < > |`）、Windows 保留设备名（CON、PRN、AUX、NUL、COM1–9、LPT1–9）、尾随点或尾随空格，或目标已存在时，阻止操作并提示原因。

### 4.3 重命名

- 重命名文档目录。
- 同步当前文档 `name` 元数据。
- 更新父文档受控链接区域。
- 使用 Obsidian 文件管理 API，尽量保持已有引用有效。

### 4.4 删除

- 删除任何文档前均显示确认提示（无论是否含子文档）。
- 确认后删除整个文档目录，包括 `index.md`、附件和所有子文档。
- 优先使用 `fileManager.trashFile`；Obsidian 版本不支持时回退 `vault.trash(folder, false)`（本地回收站）。
- 删除失败时保留侧边栏状态并显示错误。

## 5. 子文档链接

父文档的 `index.md` 使用受控区域：

```md
<!-- nestnote:children:start -->
- [文档1](文档1/index.md)
- [文档2](文档2/index.md)
<!-- nestnote:children:end -->
```

规则：

- 新建、删除和重命名子文档时更新受控区域。
- 链接按文档名称排序。
- 使用标准 Markdown 相对路径，并对特殊字符进行必要编码。
- 区域外正文完全不修改。
- 用户正文中的手写链接不主动扫描、删除或改写。
- 找不到受控区域时，在 Frontmatter 之后创建该区域。

## 6. 附件处理

插件不注册或覆盖名为“插入附件”的命令，保留 Obsidian 原生命令。

插件监听 Vault 文件创建事件，并结合当前打开的文档判断新建附件的归属：

1. 当前活动文件是某个已识别完整文档的 `index.md`。
2. 原生命令创建了附件。
3. 附件尚未位于该文档的 `attachments/` 下。
4. 来源为当前文档目录的直接子文件、Vault 根目录，或解析后的 Obsidian `attachmentFolderPath`（`vault.getConfig("attachmentFolderPath")` / `vault.config.attachmentFolderPath`，支持 `./` 相对当前文档目录）。`fileManager.getNewFileParent(sourcePath)` 是 1.5.x 新笔记位置 API，不得当作附件目录，也不得覆盖 `attachmentFolderPath`；仅在读不到该配置时可作为带附件路径的补充探测。
5. 使用可用路径策略解决文件名冲突。
6. 移动后更新引用，避免留下失效路径。

**绝不移动：** 已位于其他完整文档 `attachments/` 下的文件、位于其他完整文档目录内的文件、无法判断的路径。Vault `create` 事件对无法归属的普通新图片静默保留，不刷屏 Notice。手动命令「NestNote：归档当前附件」失败时可以 Notice。

插件可提供名称明确的备用命令“NestNote：归档当前附件”，但不注册同名原生命令。所属文档仍按附件路径向上解析。

## 7. 扫描与事件同步

### 7.1 启动扫描

插件加载后扫描整个 Vault：

1. 收集目录和文件结构。
2. 识别完整文档目录。
3. 递归构建文档树。
4. 同步文档名称元数据。
5. 更新父文档的受控子文档链接区域。

### 7.2 运行时事件

监听文件创建、删除、重命名和修改事件。连续事件进行短暂合并（防抖），避免短时间内重复触发。

**MVP 实现：** 合并后的每次刷新均执行全量 `scanDocuments`（扫描整个 Vault 并重建文档树），同步 Frontmatter 与受控链接，再更新侧边栏。协调器虽记录受影响路径，但当前版本未实现按分支的增量刷新。

插件写入文件时使用内部操作标记，防止自己的写入触发无限同步循环。

**后续优化（非 MVP）：** 按受影响路径仅重新计算相关文档分支，以减少大型 Vault 的扫描开销。

### 7.3 并发与冲突

- 外部文件变更与插件同步同时发生时，以最新文件内容为准。
- 不覆盖用户正文。
- 创建和重命名使用目标路径冲突检查。
- 文件移动或删除失败时提示用户，不伪造成功状态。

## 8. 建议的模块边界

- `DocumentScanner`：识别完整文档并构建树。
- `DocumentService`：创建、重命名、删除和打开文档。
- `FrontmatterService`：读取和同步 `name`、`created`。
- `ChildrenLinkService`：生成和更新受控子文档链接。
- `AttachmentService`：监听和归档新建附件。
- `VaultEventCoordinator`：合并事件并触发全量重新扫描。
- `DocumentTreeView`：渲染侧边栏和处理用户操作。
- `main.ts`：插件生命周期、命令和模块装配。

模块通过明确的服务接口协作，文件系统作为唯一持久化状态。

## 10. MVP 非目标

- 不自动修复不完整目录。
- 不转换普通 Markdown 文件。
- 不显示未归档文件。
- 不依赖 Dataview 或其他第三方插件。
- 不维护独立的 JSON 数据库或缓存索引。
- 不改写受控区域以外的用户正文。

## 12. 已知限制

- **全量扫描：** MVP 在 Vault 事件触发后重新扫描整个 Vault，而非按受影响分支增量刷新（见 §7.2）。
- **新建入口差异：**
  - 侧边栏工具栏「新建文档」与命令 `nestnote:new-document` 始终在 Vault 根创建。
  - 侧边栏文档行「新建子文档」以该行文档为父节点。
  - 命令 `nestnote:new-child-document` 须先打开父文档 `index.md`，按当前活动文件所属文档创建，不读取侧边栏选中态。
- 附件自动归档仅在能安全关联到当前活动 `index.md` 时触发；允许来源为当前文档目录直接子文件、Vault 根目录、或解析后的 `attachmentFolderPath`（含 `./` 相对路径）。`getNewFileParent(sourcePath)` 不作为附件目录。其他完整文档目录/`attachments/` 与无法判断的路径绝不移动；Vault 创建事件对此静默保留，手动归档命令失败时可 Notice。
- 插件不注册名为「插入附件」的命令，保留 Obsidian 原生命令。
- 删除优先 `fileManager.trashFile`；旧版本 Obsidian 回退 `vault.trash(..., false)`（本地回收站），不读取「系统回收站」偏好。
- Obsidian 可能为命令 ID 自动加上插件前缀（如 `nest-note:nestnote:open-document-tree`）。
